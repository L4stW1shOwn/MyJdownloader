# ADR-012: Local API transport

- **Status**: Accepted
- **Date**: 2026-11-14
- **Amended**: 2026-11-14 (T-071)

## Context

ADR-006 restricted v1 to the `api.jdownloader.org` relay and deferred a
direct LAN connection to the backlog. The goal behind that item is to drive a
self-hosted JDownloader **without depending on jdownloader.org**: no
MyJDownloader account, no traffic leaving the local network, and calls that
keep working when the relay or the internet link is down.

The MyJD direct connection (`getDirectConnectionInfos`) does not meet that
goal: login, device listing, session renewal (regaintoken) and
`getDirectConnectionInfos` itself all go through `api.jdownloader.org`; only
the action calls would go direct.

JDownloader also ships a **local API** (the "Deprecated API" server, default
port 3128). Verified in the JDownloader source:

- `DeprecatedAPIServer` listens on the port set in JDownloader's advanced
  settings, localhost-only unless the user opens it, and accepts plain HTTP or
  TLS on the same port (the first bytes are sniffed). TLS is **TLS 1.2 only**
  with a **self-signed** RSA-2048 certificate generated by the device.
- There is **no authentication** and no payload encryption.

Observed in a live capture on 2026-11-14 against JDownloader core revision
48637 (read-only calls):

- **Same namespaces and action paths** as MyJD (`/jd/version`,
  `/device/ping`, `/downloadsV2/queryPackages`, `/system/getSystemInfos`,
  `/events/listpublisher`, `/contentV2/getIcon`).
- **Request**: `GET` and `POST` are both accepted. With `POST <path>` and the
  body `{"params":[...]}`, each parameter is a **raw JSON value**; an object
  passed as a JSON string (the relay convention) is rejected with
  `BAD_PARAMETERS`. Extra members (`url`, `rid`, `apiVer`) are ignored. An
  empty body or `{"params":[]}` works for parameterless actions.
- **Success**: HTTP 200, body `{"data": <value>}`. **`rid` is never echoed**.
  An action without return value answers `{"data":""}`: the `data` member is
  always present.
- **Device errors**: HTTP 4xx with a JSON body
  `{"src":"DEVICE","type":"<TYPE>","data":<value or null>}`
  (`404 API_COMMAND_NOT_FOUND`, `400 BAD_PARAMETERS`).
- **Non-JSON errors**: an unknown namespace gives `501` with an empty body; a
  malformed request body gives `500` with a **Java stack trace** as plain
  text; a reverse proxy in front gives its own HTML pages.
- **Binary** (`/contentV2/getIcon`): HTTP 200, `image/png`, raw PNG bytes, as
  on the relay path (ADR-011).

## Decision

- **Local API transport instead of the MyJD direct connection**: it is the
  only approach that removes the jdownloader.org dependency. The MyJD direct
  connection is dropped; it may come back as its own backlog item.
- **Packaging**: in the **core package**, namespace **`MyJdownloader.Local`**.
  The local transport adds no dependency (ADR-002 splits packages by
  dependency), and a separate package would force a public `JDownloaderDevice`
  factory and a public `IBinaryDeviceChannel` in the core.
- **Public surface** (additive only, minor release):
  - `LocalJDownloaderOptions` (sealed, settable properties like
    `MyJDownloaderOptions`): `BaseAddress` (absolute, `http` or `https`, no
    user info, no query or fragment, path prefix allowed; default
    `http://127.0.0.1:3128`), `AllowUnencryptedRemoteHost` (default `false`),
    and `MaxResponseBodyLength` (default 1 048 576, at least 1 024, same
    meaning as `MyJDownloaderOptions.MaxResponseBodyLength`).
  - `LocalJDownloaderClient(HttpClient httpClient, LocalJDownloaderOptions? options = null)`,
    validating the options synchronously (`ArgumentException` whose message
    does not contain the address), with a `JDownloaderDevice Device` property
    (`Id` = `"local"`) exposing the existing typed facades. No connect,
    disconnect or session.
- **Internal channel** `LocalDeviceChannel : IDeviceChannel, IBinaryDeviceChannel`,
  reusing the existing argument limits and snapshot rules:
  - **Request**: always `POST <base address><path>`, `Content-Type:
    application/json; charset=utf-8`, body `{"params":[...]}` with every argument written as
    its **raw JSON value**. `POST` with a body keeps arguments out of URLs
    (proxy and access logs) and out of URL length limits.
  - **No `rid`, no `apiVer`** are sent, and no `rid` check exists on this
    path: the device never echoes it and there is no encryption layer to bind
    a response to its request; HTTP request/response pairing is the only
    correlation.
  - **Success**: the `data` member of the envelope is deserialized with the
    caller's `JsonTypeInfo<T>` (same `null` semantics as the relay). The
    media type of a 200 JSON answer is **not checked**: the `{"data": ...}`
    envelope is the guard.
  - **Device errors** (non-2xx with a JSON body carrying `type`): mapped
    through the existing `MyJdErrorMapper`, giving the same exceptions as the
    relay path (ADR-005).
  - **Anything else** (non-2xx without such a body, 3xx, a 200 body that is
    not the envelope): `MyJdProtocolException` whose message carries the HTTP
    status code only. **Error bodies are never surfaced**: the response body
    (stack trace, proxy HTML) is never copied into an exception.
  - **Binary**: the raw bytes after the ADR-011 checks (`image/png`, PNG
    signature, size cap).
  - Absolute URIs are always built from `BaseAddress` (a caller-set
    `HttpClient.BaseAddress` is ignored); redirects are not followed by the
    library (callers keep `AllowAutoRedirect = false`, as in ADR-003), and the
    final request URI must keep the base address scheme, host and port.
- **Cleartext only to loopback**: plain `http` is rejected for a host that is
  not a loopback address unless `AllowUnencryptedRemoteHost` is set. The
  check is synchronous, without DNS. Loopback means the host name `localhost`
  (case-insensitive), any IPv4 `127.0.0.0/8` literal, `::1` and IPv4-mapped
  loopback (`::ffff:127.x.x.x`). Anything else, private LAN addresses
  included, needs `https` or the opt-in.
- **No certificate handling in the library**: it never disables certificate
  validation. For `https` to the self-signed JDownloader certificate, the
  documented way is certificate pinning on the **caller's handler**
  (`SocketsHttpHandler.SslOptions.RemoteCertificateValidationCallback`
  comparing the SHA-256 of the presented certificate with a pinned value).
  Authentication to a reverse proxy goes through the caller's
  `HttpClient.DefaultRequestHeaders` or handler, with no new public surface.
- **Dependency injection**. Original decision: "No DI registration in this
  iteration: `MyJdownloader.Extensions.DependencyInjection` is unchanged; a
  named-client registration may follow as a separate item."
  Amendment (T-071): `AddLocalJDownloader` in
  `MyJdownloader.Extensions.DependencyInjection` registers the
  `LocalJDownloaderOptions` binding and a `LocalJDownloaderClient` singleton
  (`TryAdd`) over a named client, `LocalJDownloaderServiceCollectionExtensions.HttpClientName`
  (`"MyJdownloader.Local"`), built as ADR-003 prescribes: `AllowAutoRedirect = false`,
  all HTTP loggers removed, `PooledConnectionLifetime` of two minutes, and no
  handler rotation. Unlike the relay registration, redirects are disabled
  again in a `PostConfigure` of the client factory options, so a later handler
  configuration (returned builder, `ConfigureAll`, a second registration of
  the name) cannot re-enable them on a `SocketsHttpHandler` or an
  `HttpClientHandler`; a primary handler of another type is left as it is
  (T-071 security audit). It was motivated by the T-030 security audit: a client that
  follows redirects would send the cleartext POST body, which can hold link and
  archive passwords, to another host when whatever answers on the local port
  redirects it, before the library rejects the answer. `JDownloaderDevice` is
  not registered: the relay client also produces such instances, so a
  registration would be ambiguous when both clients share a container. Use
  `client.Device` instead.
- No logging; no account credential or session exists on this path. Request
  bodies may carry link and archive passwords.

## Considered alternatives

| Alternative | Reason for rejection |
|---|---|
| MyJD direct connection (`getDirectConnectionInfos`) | Login, device listing, renewal and discovery still go through `api.jdownloader.org`; it keeps the account and the jdownloader.org dependency. |
| Direct connection first, then the local API | Delays the only approach that meets the goal and adds a transport that would then be superseded. |
| Separate `MyJdownloader.Local` package | No dependency justifies it (ADR-002); it needs a public `JDownloaderDevice` factory and a public `IBinaryDeviceChannel` (more frozen public API) and a third package in the release workflow. |
| `GET` with URL-encoded arguments | Arguments would appear in URLs (proxy and access logs) and be bound by URL length limits. |
| Parameters as JSON strings, like the relay | Rejected by the device with `BAD_PARAMETERS`. |
| Sending and checking `rid` | The device never echoes it; the check cannot exist. |
| Plain HTTP allowed to any host by default | The local API has no authentication and no encryption; a silent cleartext LAN exposure is a failure. |
| Disabling certificate validation, or a built-in trust option | Weakens TLS inside the library; pinning on the caller's handler keeps the trust decision with the caller (ADR-003). |
| Copying error bodies into exceptions | They may hold Java stack traces or proxy pages; they are unreadable and leak internal details. |
| Checking the media type of 200 JSON answers | Adds a failure mode without protection: the `{"data": ...}` envelope already rejects non-JSON payloads. |

## Consequences

Positive:

- A self-hosted JDownloader can be driven with no account and no call to
  jdownloader.org, through the same typed facades.
- Additive public API (two types), no new dependency, AOT and BCL only; the
  relay path is unchanged.
- Error mapping, argument limits, response size caps and the binary checks
  are shared with the relay path (ADR-005, ADR-011).
- Safe defaults: cleartext only to loopback, certificate validation never
  disabled, error bodies never surfaced, arguments never in URLs.

Negative:

- The local API has **no authentication** and no payload encryption:
  confidentiality and access control rely entirely on the network, TLS and
  whatever the caller or a reverse proxy adds.
- No `rid` binds a response to its request; integrity relies on the HTTP
  connection (and TLS when used).
- Pinning the self-signed certificate is left to the caller and must be
  redone when the device regenerates its certificate.
- The loopback check is lexical: a host name resolving to loopback other than
  `localhost` still needs `https` or the opt-in.
- The local API is labelled "Deprecated" by JDownloader and may change or
  disappear independently of the MyJD protocol.
- A second `IDeviceChannel` implementation to maintain and test.
