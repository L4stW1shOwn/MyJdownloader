# Local API

This guide shows how to drive a JDownloader device through its own local HTTP
API with `LocalJDownloaderClient`, without a MyJDownloader account and without
the relay at `api.jdownloader.org`. It covers when this path is the right
choice, how to enable the API on the device, the usages on the same machine and
on another host, and what this path does not provide.

> **Warning: the local API has no authentication and no encryption.** Anyone who
> can reach its port controls JDownloader: they can add links, start downloads,
> restart the device and read its settings. Traffic in plain `http` can be read
> and altered on the way. "Anyone" includes every process on the same machine,
> other containers on the same Docker network, and a web page that makes the
> browser of a user on that machine send requests to the port. Keep the port on loopback, or on a network you trust,
> or put it behind `https` and an authenticating reverse proxy.

## When to use it

Use `LocalJDownloaderClient` when the application and the JDownloader device are
under your control and you want the calls to stay on your network.

| | Relay client (`MyJDownloaderClient`) | Local client (`LocalJDownloaderClient`) |
|---|---|---|
| Account | MyJDownloader account required | None |
| Route | MyJDownloader relay (`api.jdownloader.org`) | Directly to the device |
| Session | Connect, session export, automatic renewal | None: nothing to connect or disconnect |
| Encryption | Encrypted payload | None; use `https` when the path leaves the machine |
| Authentication | Account credentials | None on the device; add it at a reverse proxy if needed |
| Device listing | `GetDevicesAsync` | Not available: you already know the address of the one device |
| Works when the relay or the internet link is down | No | Yes, on the local network |

The local API is labelled "Deprecated" by JDownloader. It may change or disappear
independently of the MyJDownloader protocol. The typed facades are the same on
both paths, so the calls in the other guides apply once you have a
`JDownloaderDevice`.

## Enable the local API

In JDownloader, open the advanced settings and filter on `RemoteAPI`. The
options are:

- `Deprecated Api Enabled`: turns the local API on.
- `Deprecated Api Localhost Only`: when on, the API listens on the loopback
  interface only. Turn it off only when the caller is on another machine or
  inside a container (see below).
- `Deprecated Api Port`: the TCP port, `3128` by default.

The labels above are approximate and may differ between JDownloader versions:
look for the `RemoteAPI` entries if the names are not the same on your build.

JDownloader serves plain HTTP and TLS on the same port. The TLS certificate is
generated by the device, is self-signed, and TLS 1.2 is the only version it
accepts.

## Docker

A port published with `-p` or `ports:` reaches the container's network interface,
not its loopback. With `Deprecated Api Localhost Only` on, the API listens on the
container's loopback and the published port cannot reach it. Turn the option off
inside the container, and publish the port on the host's loopback interface only,
so that the API stays off the network:

```shell
docker run -p 127.0.0.1:3128:3128 <your-jdownloader-image>
```

The application on the host then uses `http://127.0.0.1:3128`, as in the next
section.

## Same machine: default options

When the application runs on the machine where JDownloader runs (or on the host
that publishes the port on loopback), the defaults are enough. The base address is
`http://127.0.0.1:3128`, and cleartext is accepted because the host is loopback.

```csharp
using MyJdownloader;
using MyJdownloader.Local;

// Keep the HttpClient for the lifetime of the application.
using var http = new HttpClient(new SocketsHttpHandler
{
    AllowAutoRedirect = false, // redirects are not followed; keep this
});

var client = new LocalJDownloaderClient(http); // http://127.0.0.1:3128
JDownloaderDevice device = client.Device;

long version = await device.Jd.GetVersionAsync();
Console.WriteLine($"JDownloader version {version}");

bool alive = await device.Device.PingAsync();
int speed = await device.DownloadController.GetSpeedAsync();
int packages = await device.Downloads.GetPackageCountAsync();
```

`client.Device` has the same facades as a device from the relay client. The
client keeps no state, so one instance can serve the whole application.

## Another host

When JDownloader runs on another machine, the address is no longer loopback, and
the client refuses `http` for it unless you opt in. Choose one of the three
options below. The first is the recommended one.

### Option 1: https with the device certificate pinned

Use `https` and trust the device's self-signed certificate by pinning it on the
caller's handler: the callback accepts the connection only when the SHA-256 of
the certificate the device presents equals a value you obtained beforehand. The
library never disables certificate validation: the trust decision stays with the
caller.

Get the fingerprint once, over a channel you trust (for example the device
console, or the certificate file on the device), and store it as configuration.

```csharp
using System.Net.Security;
using System.Security.Cryptography;
using MyJdownloader.Local;

// SHA-256 of the device certificate, as 64 hexadecimal characters.
var pinned = Environment.GetEnvironmentVariable("JD_CERT_SHA256")
    ?? throw new InvalidOperationException("JD_CERT_SHA256 is not set.");

var handler = new SocketsHttpHandler
{
    AllowAutoRedirect = false,
    SslOptions = new SslClientAuthenticationOptions
    {
        // The pin replaces chain validation: a self-signed certificate has no chain to validate.
        RemoteCertificateValidationCallback = (_, certificate, _, _) =>
            certificate is not null
            && string.Equals(
                Convert.ToHexString(SHA256.HashData(certificate.GetRawData())),
                pinned,
                StringComparison.OrdinalIgnoreCase),
    },
};

using var http = new HttpClient(handler);
var client = new LocalJDownloaderClient(http, new LocalJDownloaderOptions
{
    BaseAddress = new Uri("https://192.0.2.10:3128"),
});

long version = await client.Device.Jd.GetVersionAsync();
```

The device generates a new certificate in some cases, and then the pin no longer
matches: the calls fail with `HttpRequestException` (inner
`AuthenticationException`), raised by the handler and not wrapped by the
library, until you update the stored value. Compare fingerprints without
separators: remove the colons that `openssl x509 -fingerprint` prints. Update it deliberately, after you have checked the new fingerprint.

### Option 2: cleartext on a trusted network

`AllowUnencryptedRemoteHost` lets `http` address a non-loopback host. Use it only
on a network you trust, such as a private link between two machines you own. Every
call and answer then travels in clear text, and anyone on the path can read them
or send commands to the device.

```csharp
var client = new LocalJDownloaderClient(http, new LocalJDownloaderOptions
{
    BaseAddress = new Uri("http://192.0.2.10:3128"),
    AllowUnencryptedRemoteHost = true,
});
```

The check is lexical and makes no DNS lookup. A host name that resolves to a
loopback address, other than `localhost`, is still refused without the option.

### Option 3: reverse proxy with authentication

Put a reverse proxy in front of the device. The proxy terminates `https`, checks
credentials, and forwards the request to the local API. The library has no
authentication setting: send the credentials as a default request header on the
caller's `HttpClient`. Read them from a secret store, never from the source code.

```csharp
using System.Net.Http.Headers;
using System.Text;
using MyJdownloader.Local;

var user = Environment.GetEnvironmentVariable("JD_PROXY_USER")
    ?? throw new InvalidOperationException("JD_PROXY_USER is not set.");
var password = Environment.GetEnvironmentVariable("JD_PROXY_PASSWORD")
    ?? throw new InvalidOperationException("JD_PROXY_PASSWORD is not set.");

using var http = new HttpClient(new SocketsHttpHandler { AllowAutoRedirect = false });
http.DefaultRequestHeaders.Authorization = new AuthenticationHeaderValue(
    "Basic",
    Convert.ToBase64String(Encoding.UTF8.GetBytes($"{user}:{password}")));

var client = new LocalJDownloaderClient(http, new LocalJDownloaderOptions
{
    BaseAddress = new Uri("https://jd.example/jdownloader"), // path prefix of the proxy
});
```

With this option the proxy's certificate is an ordinary one, so the default
certificate validation applies and no pin is needed. The proxy answers with its
own pages on errors: the library reports those as `MyJdProtocolException` with the
HTTP status only.

## Handler settings

- Set `AllowAutoRedirect = false` on the handler. The library does not follow
  redirects: a redirect to another origin is rejected, but only after the request
  has been sent.
- Keep one `HttpClient` for the lifetime of the application. The client does not
  dispose it. For a long-lived process you can also set
  `PooledConnectionLifetime` on the handler to pick up DNS changes.
- Do not add HTTP logging to this client. Request bodies carry the arguments of
  device calls, and some of them are passwords (see
  [Logging and security](logging-and-security.md)).
- `HttpClient.BaseAddress` is ignored. Every call goes to the address in
  `LocalJDownloaderOptions.BaseAddress`.

## Limits and timeouts

- **Timeout.** `HttpClient.Timeout` bounds each call, body included. When it
  expires, the call throws `TimeoutException`. The default of `HttpClient` is
  100 seconds.
- **Response size.** `LocalJDownloaderOptions.MaxResponseBodyLength` caps the body
  of an answer. The default is 1 048 576 bytes, the minimum is 1 024, and there is no
  upper bound. A larger answer throws `MyJdProtocolException` with the message
  "The MyJD device response exceeds the configured size limit.". Raising the limit
  lets the device make the client allocate that much per call: raise it only for
  large answers, such as a long list.
- **Retries.** The library does not retry. Resilience is left to the caller (see
  [Error handling](error-handling.md)). A failed destructive action may still have
  run on the device: read the facade page before you retry it.

## Errors

The local client raises the same exception types as the relay client, with the
same hierarchy (see [Errors](../api/errors.md)).

| Situation | Exception |
|---|---|
| The device answers with an error body carrying a `type` (for example `API_COMMAND_NOT_FOUND` or `BAD_PARAMETERS`) | `MyJdApiException`, with `ErrorType` set to the code and `ErrorSource` set to `Device` |
| The same, with `AUTH_FAILED`, `EMAIL_INVALID`, `EMAIL_FORBIDDEN`, `TOKEN_INVALID` or `ERROR_EMAIL_NOT_CONFIRMED` | `MyJdAuthenticationException` |
| The same, with `OFFLINE` | `MyJdDeviceOfflineException` |
| The same, with `TOO_MANY_REQUESTS`, `OVERLOAD` or `MAINTENANCE` | `MyJdRateLimitException` |
| An answer that is not JSON, a non-2xx status without a readable error, a redirect, a `200` body that is not a JSON object with a `data` member, or a body over the size limit | `MyJdProtocolException` |
| No complete answer within `HttpClient.Timeout` | `TimeoutException` |
| The connection fails (JDownloader stopped, wrong port, TLS or pin failure) | `HttpRequestException`, raised by `HttpClient` and not wrapped; its message may name the host and port |
| Cancellation through your `CancellationToken` | `OperationCanceledException` |

The library never copies the response body into an exception. A protocol error
carries the HTTP status code only, because the body of an error answer may hold a
Java stack trace or a proxy page. Do not log response bodies yourself either.

## What does not exist on this path

- **No session.** There is no `ConnectAsync`, `DisconnectAsync`, `ExportSession`
  or `RestoreSession`, and no `SessionChanged` event.
- **No reconnection.** There is no automatic renewal and no replay of a failed
  call.
- **No device listing.** There is no `GetDevicesAsync` and no `GetDevice(id)`: the
  client drives the one device at the address you configured. `Device.Id` is
  always `local`.
- **No dependency-injection registration.** `AddMyJDownloader` does not register
  the local client. Construct it yourself, or register it manually as a singleton
  over a long-lived `HttpClient` that you own.
- **No built-in authentication, encryption or certificate option.** Those are
  provided by the network, by `https` with the caller's handler, or by a reverse
  proxy.
